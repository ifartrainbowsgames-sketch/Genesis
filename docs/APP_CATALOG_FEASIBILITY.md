# App catalog / launcher feasibility research

This document preserves the deep-research findings behind the "local app store for AI + dev tools" direction for Genesis (researched 2026-09-28). It is background/evidence for the planned work tracked in `PROJECT_STATUS.md` and the design summary in `docs/ARCHITECTURE.md` — read those first for the actual plan; this file is the supporting analysis and citations.

---

# Genesis can become a local AI app store — carefully

Building Genesis into a local-first "app store" for AI and dev tools is technically feasible and has clear architectural precedent, but the research surfaces a hard constraint that should shape the entire design: every project that tried to be a broad, one-click, "install anything" catalog either stayed narrow-scope for years (Ollama, Jan.ai, Stability Matrix, LM Studio) or went broad by abandoning safety guarantees (Pinokio, which has accumulated multiple malware/CVE incidents precisely because its manifest format is an arbitrary scripting language rather than a declarative install spec) ([Nudge Security](https://www.nudgesecurity.com/security-profile/pinokio), [GitHub Issue #880](https://github.com/pinokiocomputer/pinokio/issues/880)). No prior art combines Genesis's two stated non-negotiables — visible plans/diffs before mutation, and explicit approval for stateful calls — with a broad multi-category catalog; this is a genuinely novel architecture, not something to copy wholesale. The good news is Tauri 2's own capability/permission system already provides a real, deny-by-default enforcement boundary well-suited to this job, mature package-manager manifest schemas (Scoop, WinGet, Flatpak) already solve the declarative-manifest problem, and the legal analysis shows a defensible four-tier "bundle vs. auto-fetch vs. hand-off vs. avoid" framework exists for nearly every category of tool Genesis would want to catalog. The practical recommendation is to launch with a single narrow axis (Ollama models plus 2-3 terminals), build the transactional install/approval pipeline properly the first time, and treat catalog breadth as something to add only after the plumbing is proven — because that is exactly what every comparable project that survived actually did.

## Pinokio's breadth came at the cost of safety no one else accepted

The clearest signal in the prior-art research is a strict trade-off between catalog breadth and security architecture, and every project sits at a different point on that curve. Pinokio is a "virtual computer" built around JSON/JS scripts with a `run` array of arbitrary shell/download/file operations — this lets it wrap almost any GitHub project, but it has no execution sandbox beyond manual catalog review, and that review is shallow: a "verified" Discover-catalog script for StyleTTS 2 was found to clone a repo containing a pickle file Hugging Face itself flags as dangerous ([Nudge Security](https://www.nudgesecurity.com/security-profile/pinokio)). Users have filed repeated VirusTotal/AV-detection reports against Pinokio release artifacts ([GitHub #1039](https://github.com/pinokiocomputer/pinokio/issues/1039), [GitHub #880](https://github.com/pinokiocomputer/pinokio/issues/880)), and CVE-2025-44109 documents a URL-redirection phishing vulnerability in the Pinokio domain itself ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2025-44109/)). At the opposite end, LM Studio and Jan.ai deliberately constrain their "catalog" to metadata only — a model name mapped to a Hugging Face repo and GGUF quantization variant, no executable install recipes at all — which sharply narrows scope (models only, not apps) but eliminates Pinokio's entire risk class ([DEV Community comparison](https://dev.to/synsun/running-local-llms-in-2026-ollama-lm-studio-and-jan-compared-121c)). Ollama sits in the same safe zone: it repurposes the Docker Distribution Manifest v2 schema, pulling content-addressed SHA-256 blobs (model weights, template, license, params as separate layer types) from a registry API, which gives it free deduplication and versioning without inventing a new format or accepting arbitrary code execution during "install" ([DeepWiki: Ollama Model Registry](https://deepwiki.com/ollama/ollama/4.2-model-registry-and-layers)). Stability Matrix is the closest existing analog to what Genesis actually needs for heavier packages: each Stable Diffusion UI (ComfyUI, A1111, InvokeAI) gets its own isolated Python venv managed via `uv`, built on a plugin-style `BasePackage`/`BaseGitPackage` class hierarchy, while large model assets are centralized in a shared folder that packages symlink into rather than duplicating — a "isolate code, centralize heavy assets" split that Genesis should copy directly ([DeepWiki: StabilityMatrix architecture](https://deepwiki.com/LykosAI/StabilityMatrix)). That said, the model-sharing layer has caused real friction — filename conflicts on import, symlink-vs-junction disputes — that a Genesis design should resolve explicitly up front rather than discover via bug reports ([GitHub #991](https://github.com/LykosAI/StabilityMatrix/issues/991)).

Two more reference points matter for the packaging layer specifically. JetBrains Toolbox App runs a small always-on background daemon (`jetbrainsd`) at user-level privileges with no external ports opened, handling URI interception and IDE download/update/launch coordination — a directly reusable pattern for a minimal Genesis desktop companion process ([JetBrains Toolbox docs](https://www.jetbrains.com/help/toolbox-app/jetbrainsd.html)). And Docker Desktop Extensions demonstrate, via a real fixed CVE, that a "reviewed marketplace" is not itself a security boundary: extensions' UI panels are sandboxed, but their backends run with full host Docker Engine and filesystem access, and a genuine container-escape vulnerability through that exact IPC surface forced Docker to flip the "Marketplace-only" setting to enabled-by-default only after the fact ([SensePost](https://sensepost.com/blog/2023/an-offensive-look-at-docker-desktop-extensions/); [Docker CVE listing](https://www.cvedetails.com/vulnerability-list/vendor_id-13534/product_id-84333/Docker-Desktop.html)). The lesson for Genesis is explicit: curation and sandboxing are two independent, both-necessary controls, and a "verified" badge substitutes for neither.

## Licensing sorts cleanly into four tiers, but proprietary IDEs demand a hand-off, not a bundle

The legal research produces a defensible, reusable tiering that should become Genesis's actual catalog-policy schema field, not just a one-time analysis. **Tier (a), safe to bundle/redistribute directly**, covers everything permissively licensed: Ollama, llama.cpp, and whisper.cpp are all MIT ([Llama.cpp Wikipedia](https://en.wikipedia.org/wiki/Llama.cpp); [ggml-org discussion](https://github.com/ggml-org/llama.cpp/discussions/6394)), as are Windows Terminal, Alacritty (dual Apache-2.0/MIT), and WezTerm (MIT) ([Alacritty Wikipedia](https://en.wikipedia.org/wiki/Alacritty)). VS Code itself, critically, is **not** in this tier even though its source is MIT — Microsoft's official binary carries a proprietary license that explicitly "prohibits bundling or redistributing the official installer," while a self-built "Code - OSS" binary (no Microsoft branding, telemetry, or Marketplace access) carries none of those restrictions ([VS Code license](https://code.visualstudio.com/license); [Wikipedia](https://en.wikipedia.org/wiki/Visual_Studio_Code)). A 2018 GitHub issue shows this is a real, still-unresolved point of friction even for sympathetic use cases (a robotics-education nonprofit asking Microsoft to relax the clause for offline bundles) ([microsoft/vscode#60205](https://github.com/microsoft/vscode/issues/60205)). **Tier (b), auto-download from the vendor's official source and silently install**, fits JetBrains IDEs specifically via JetBrains' own Toolbox CLI, which explicitly documents silent-install support since Toolbox 2.4 — because directly redistributing JetBrains "Redistributable Products" triggers a contractual requirement that every end user be independently bound by a JetBrains agreement, an obligation a hobby project cannot practically discharge ([JetBrains Toolbox Subscription Agreement](https://www.jetbrains.com/legal/docs/toolbox/license/); [silent installation docs](https://www.jetbrains.com/help/toolbox-app/toolbox-app-silent-installation.html)). Vendor-hosted model downloads through official channels (Ollama's own pull mechanism, Hugging Face repos) also belong here. **Tier (c), fetch the official installer and hand off execution to the user**, is the safest default for proprietary or legally ambiguous tools — Microsoft VS Code and Cursor both land here, the latter because its Terms of Service were only partially retrievable in this research and no explicit clause on third-party automated installation was found, meaning "unconfirmed" should default to the conservative tier rather than being read as permission ([Cursor Community Forum](https://forum.cursor.com/t/api-sdk-terms-of-use-question/159741)). **Tier (d), avoid automating or deep-link only**, covers research-only/non-commercial model licenses and any download flow that would require evading bot-detection or CAPTCHAs to automate.

The legal basis for tier (c) is stronger than it might first appear: under *hiQ Labs v. LinkedIn*, automated fetching of otherwise-publicly-downloadable content does not by itself trigger CFAA liability, because courts apply a "gates-up-or-down" framework keyed to technical access barriers, not written policy ([hiQ Labs v. LinkedIn](https://en.wikipedia.org/wiki/HiQ_Labs_v._LinkedIn)) — though the same line of cases confirms a vendor's anti-automation ToS clause remains independently enforceable as a *contract* matter, which is why Genesis should never build a feature that evades rate-limiting or CAPTCHAs to force an installer download ([White & Case analysis](https://www.whitecase.com/insight-our-thinking/web-scraping-website-terms-and-cfaa-hiqs-preliminary-injunction-affirmed-again)). Model weights need their own per-file license tagging independent of runtime licensing: llama.cpp being MIT says nothing about whether a given GGUF file is Apache-2.0 (many newer Mistral releases) or carries Meta's Llama Community License, which requires redistributors to include the license text, display "Built with Llama," and retain a Notice file — obligations Genesis would inherit the moment it bundles Llama-family weights directly rather than letting Ollama's own registry serve them ([Meta Llama 3.1 License](https://www.llama.com/llama3_1/license/)). Trademark risk is comparatively low: showing a tool's name and unmodified logo in a catalog listing is textbook nominative fair use, provided the UI never implies official sponsorship or endorsement ([Fair use (Trademark law) - Wikipedia](https://en.wikipedia.org/wiki/Fair_use_(Trademark_law))). On takedown precedent, no primary source documents winget, Homebrew, or Chocolatey being DMCA'd or cease-and-desisted over redistributing a proprietary tool's installer — plausibly *because* they already follow the tier-(b)/(c) "point at vendor's URL, download at install time" pattern rather than embedding vendor binaries — but the 2020 RIAA takedown of youtube-dl (later reversed with EFF's help) is a useful cautionary analog: even a tool that only automates fetching publicly available content can face a takedown attempt on a weak legal theory ([EFF: GitHub Reinstates youtube-dl](https://www.eff.org/deeplinks/2020/11/github-reinstates-youtube-dl-after-riaas-abuse-dmca)). Separately, a comparable local-AI launcher, Stability Matrix, was actually removed from Patreon under a policy against "AI tools that can produce explicit imagery" — not because of anything in its own catalog, but because of what downstream tools it launches *could* generate — which is a platform-policy risk distinct from copyright law and one Genesis should anticipate if it ever integrates payments or a third-party app-store distribution channel.

## A manifest needs WinGet's fields, Flatpak's permission block, and Tauri's ACL as the enforcement layer

Mature manifest formats converge on the same core fields — identifier, semver, download URL(s), integrity hash, install/uninstall mechanics, platform gating — but differ sharply in whether they carry sandboxing metadata inline. Scoop's JSON manifests require `version`, `description`, `homepage`, `license`, plus `url`/`hash` (SHA-256), `bin`, `depends`, lifecycle scripts, and `checkver`/`autoupdate` fields for automated drift detection ([Scoop schema.json](https://github.com/ScoopInstaller/scoop/blob/master/schema.json)). WinGet's YAML manifests add `InstallerSwitches.Silent` (the literal unattended-install flags passed to the underlying installer), `Scope` (user vs. machine), and `ProductCode`/`AppsAndFeaturesEntries` for uninstall correlation ([winget-pkgs schema 1.6.0](https://github.com/microsoft/winget-pkgs/blob/master/doc/manifest/schema/1.6.0/installer.md)). Flatpak is the one format that bakes sandbox permissions directly into the manifest via a `finish-args` block — flags like `--filesystem=xdg-documents` (portal-scoped, not blanket home access), `--socket=wayland`, `--device=dri` — and Flathub's review process treats broad grants as flagged exceptions, mandating the XDG-portal path over a static permission whenever a portal exists for the use case ([Flathub App Requirements](https://github.com/flathub/flathub/wiki/App-Requirements)). None of these formats has a first-class field for estimated disk space or RAM requirements — a genuine gap Genesis will need to originate itself, likely computed empirically from observed installs rather than trusted from the manifest.

The synthesized recommendation is a hybrid manifest: WinGet/Scoop-style identity, version, source, checksum, and silent-install-switch fields; npm-style `bin`/`launch` and `engines` fields for platform-compatibility declarations; a Docker Compose-style `healthcheck` block to verify a launched tool is actually running, not just that install "succeeded"; and a Flatpak-style declarative permissions block that becomes the literal approval screen shown to the user before install — mapping directly onto Genesis's "plans and diffs visible before changes are applied" rule. Installed-state tracking should follow the DNF/RPM pattern of a local SQLite transaction log (not a flat JSON file, which offers no atomic multi-row guarantee) with explicit execute → commit → rollback phases, so a failed install unwinds deterministically in reverse order ([oneuptime.com DNF History guide](https://oneuptime.com/blog/post/2026-03-04-rollback-package-updates-dnf-history-rhel-9/view); [US8978028B2 patent](https://patents.google.com/patent/US8978028)). Concretely: an `installed_apps` table (app_id, version, install_path, checksum, status) and an `install_transactions` table (transaction_id, app_id, phase, error_detail), with the real install location only touched after checksum verification against the manifest succeeds.

On sandboxing, the research is unambiguous that Genesis should not attempt to build a container/namespace runtime from scratch. Realistic tiers, cheapest first: run installed apps as ordinary user processes with install scoped to a workspace-local directory (Tier 0, do this first); on Linux, shell out to `bwrap` directly for apps that declare a sandbox profile, since bubblewrap is a single unprivileged binary rather than a subsystem Genesis has to build, and its unprivileged design (no SUID binary) is a materially better security posture than Firejail's SUID-root approach, which has had real privilege-escalation CVEs (CVE-2022-31214) ([containers/bubblewrap](https://github.com/containers/bubblewrap)); on Windows, generate per-app Windows Sandbox `.wsb` configs for install-time inspection, accepting that persistent use is awkward since state resets on close. A full custom namespace/seccomp engine, or a general MSIX/AppContainer pipeline for arbitrary third-party binaries, is explicitly "enormous engineering" territory out of scope for a small team.

This is where Tauri 2's own architecture becomes the load-bearing security boundary rather than an implementation detail. Tauri 2's ACL model is genuinely default-deny and three-layered — capabilities (which window gets which permissions), permissions (which commands are allowed), and scopes (fine-grained constraints on what a permitted command can touch, expressed as regex-validated argument patterns or glob-restricted filesystem paths) ([Tauri v2 Capabilities docs](https://raw.githubusercontent.com/tauri-apps/tauri-docs/v2/src/content/docs/security/capabilities.mdx)). Critically, `shell:allow-execute` requires an explicit allow-list scope with no wildcard by default, so Genesis cannot accidentally grant a generic "run any downloaded binary" permission without deliberately opting into a scope that defeats the model. The recommended split is: put the actual privileged operations (download, checksum-verify, extract, launch, sandbox-invoke, install-state writes) in Rust/Tauri commands behind narrowly-scoped `tauri-plugin-shell`/`tauri-plugin-fs` capabilities — one scoped entry per class of install action, never a general `sh -c` passthrough — while FastAPI stays responsible for catalog-index fetching, manifest schema validation, semver-diff computation, and approval-token issuance/audit logging, with Next.js only calling FastAPI for planning data and Tauri's `invoke` for already-approved execution. This gives Genesis defense in depth: the approval boundary is enforced twice, once logically in FastAPI and again structurally at the Tauri IPC boundary, so even a compromised frontend or backend cannot execute anything outside the pre-declared, build-time-fixed action space. The approval token itself should be scoped to `(app_id, version, manifest_hash)`, not just `app_id`, so a catalog update carrying new permissions never silently inherits an old approval.

## Wrap native package managers first; build a custom fetch-and-run path only for the long tail

On packaging tools specifically, the trade-off is stark and well-evidenced. Delegating installs to `winget install --silent`, `flatpak install -y --noninteractive`, `brew install`, or `apt-get install -y` inherits each ecosystem's existing catalog breadth, checksum/signature verification, and — critically on Windows — its Authenticode/SmartScreen reputation, since Windows SmartScreen reputation is per-file/per-publisher and cannot be purchased or bypassed even with EV certificates as of Microsoft's 2024 policy change ([Microsoft Learn: SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation); [DigiCert](https://knowledge.digicert.com/alerts/ev-signed-application-showing-microsoft-defender-smartscreen-warnings)). A fully custom fetch-and-execute engine, by contrast, cold-starts every third-party binary at zero SmartScreen reputation indefinitely, regardless of how well-signed Genesis itself is — a durable, ongoing "scary warning" UX problem the wrapper approach avoids entirely. The cost of wrapping is real but bounded: `--silent` behavior is only as good as what each installer's own manifest declares (winget-cli maintainers acknowledge this directly, [winget-cli#3891](https://github.com/microsoft/winget-cli/issues/3891)), so Genesis cannot promise a universally dialog-free install and must surface that possibility during approval; and Linux is inherently fragmented between apt (distro-specific) and Flatpak (sandboxed, distro-agnostic), likely requiring Genesis to detect and support both paths rather than one. On Windows specifically, winget also ships a COM API (`WindowsPackageManager.Interop`) as a structured alternative to parsing CLI stdout, trading portability for cleaner native interop ([microsoft/winget-cli](https://github.com/microsoft/winget-cli)).

The realistic hybrid: use native package managers wherever a tool is cataloged there (best coverage, inherited trust, least custom code), and fall back to a custom, tightly-scoped fetch/verify/launch path — built as one narrowly-scoped, auditable Tauri command with user approval, using Rust crates like `self_update` (checksum verification, transactional multi-file install with rollback) — only for tools absent from every native catalog ([crates.io self_update](https://crates.io/crates/self_update)). For Genesis's own self-update flow, Tauri's `tauri-plugin-updater` mandates minisign signature verification on every artifact and supports a simple static-JSON manifest hosted on GitHub Releases, consistent with the local-first, no-server-dependency ethos — but a 2026 CVE (CVE-2026-95625, CVSS 5.9) is directly relevant: the manifest's version/URL fields are fetched over TLS but never themselves signed, so an attacker able to serve a crafted manifest can force a downgrade to an older, still-validly-signed release ([Vulners CVE-2026-95625](https://vulners.com/cvelist/CVELIST:CVE-2026-95625)). Genesis should pin TLS to a known host and add an out-of-band integrity check on the manifest itself before relying on this plugin, and should not carry the same trust assumption over to third-party catalog manifests. Tauri sidecars (bundling external binaries at build time, keyed by target triple) are the right mechanism for Genesis's *own* trusted helper binaries but cannot solve the "install any third-party tool" problem, since every tool would need pre-bundling per platform at Genesis's own build time — infeasible for an open-ended catalog. Architecturally, GDLauncher's migration from a pure-Electron core to a Rust-based core handling all networking/filesystem/launch logic behind a thin SolidJS frontend via RPC is a validated precedent for exactly Genesis's existing Tauri shape: download-queue and install-state logic belongs in the Rust backend, with the frontend only rendering progress events pushed over IPC ([DeepWiki GDLauncher-Carbon](https://deepwiki.com/gorilla-devs/GDLauncher-Carbon)).

## Scope to one axis first, and treat install/update as security-critical from day one

Every comparable project that survived started narrow and left breadth to a pull mechanism rather than founder curation. Ollama's v0.0.1 was an "early preview" CLI for pulling and running GGUF models, nothing more ([Ollama v0.0.1](https://github.com/ollama/ollama/releases/tag/v0.0.1)); Jan.ai, years into development, is still scoped to local chat models with cloud APIs as an explicit opt-in bridge, not a general tool catalog ([roundproxies.com](https://roundproxies.com/blog/jan-ai/)); Stability Matrix, even as a self-described "package manager," restricts itself to a short, explicit list of Stable Diffusion UIs rather than anything general ([Stability Matrix supported packages](https://docs.lykos.ai/stability-matrix/package-manager/supported-packages)). The one project that did go broad — Pinokio — did it by shifting curation and vetting burden onto users and third-party script authors, which is precisely the trade-off Genesis's AGENTS.md is designed to avoid. The clear MVP recommendation: scope v1 to Ollama-compatible models as the primary install target (reusing an existing, actively-maintained upstream registry instead of hosting/vetting binaries) plus 2-3 terminal emulators (MIT/Apache-licensed, simple process launches, minimal supply-chain surface), and defer IDEs, vision models, and the broader "everything" catalog until the install/approval/transaction pipeline is proven in production.

That pipeline needs to be built as security-critical from the start, because the risk register here is not hypothetical. Ollama's own model-pull pipeline has had a real, actively-exploited RCE chain: CVE-2024-37032 ("Probllama") let a malicious registry manifest's path-traversal digest field achieve arbitrary file read/write via `/api/pull`, and this was one of at least three related bug classes in Ollama's model-loading code over multiple years, with a GitHub issue describing "unauthenticated arbitrary model injection... under active exploitation in the wild" ([Wiz.io Probllama](https://www.wiz.io/blog/probllama-ollama-vulnerability-cve-2024-37032); [dev.to bug-class retrospective](https://dev.to/alejandxr/ollama-model-loading-rce-three-years-of-the-same-bug-class-one-self-hosted-llm-runtime-4cae)). This means the manifest-parsing and archive-extraction code path in Genesis's own catalog engine needs the same security scrutiny as its sandboxing/approval UX — path-traversal and ZipSlip-style bugs are a proven, recurring failure mode in exactly this product category, not a theoretical one. The npm September 2025 incident, where 18 widely used packages (chalk, debug, strip-ansi) were compromised via maintainer-account phishing and shipped wallet-stealing code to "billions of weekly downloads," reinforces that a solo or small-team maintainer holding catalog-publish credentials is itself a high-value target ([Palo Alto Unit42](https://www.paloaltonetworks.com/blog/cloud-security/npm-supply-chain-attack/)). A cheap, concrete mitigation with real precedent is Pinokio's own "Bluefairy" — a default 72-hour freshness delay before newly published or updated catalog entries become installable, giving the community time to flag a compromised release before end users are exposed ([getprompting.com Pinokio safety guide](https://getprompting.com/is-pinokio-safe/)). On maintenance, the winget-pkgs/Homebrew-Cask/Scoop ecosystems all solve catalog staleness through automation rather than manual curation — Scoop's `checkver`/`autoupdate` manifest fields, Homebrew's `brew audit --online` CI gate that verifies every download URL still resolves before merge, and winget-pkgs' "wingetbot" that auto-files (but does not auto-merge) PRs when a manifest's hash drifts from upstream ([ScoopInstaller Wiki](https://github.com/ScoopInstaller/Scoop/wiki/App-Manifest-Autoupdate); [Homebrew/homebrew-cask discussion #4636](https://github.com/orgs/Homebrew/discussions/4636)) — and this is directly replicable for Genesis via a scheduled GitHub Actions job from day one, routing all bot-generated PRs through the same human-approval gate as manual submissions, since even Microsoft's bot has documented failure modes (misreading version strings) ([winget-pkgs#381256](https://github.com/microsoft/winget-pkgs/issues/381256)).

## Conclusion

The research converges on a counterintuitive but well-supported conclusion: Genesis's competitive advantage in this space is not catalog breadth, which every comparable narrowly-scoped project deliberately avoided at launch, but the approval/audit architecture that AGENTS.md already mandates and that no existing local-AI launcher has actually built. Pinokio proved a broad catalog is achievable but only by discarding exactly the safety guarantees Genesis is committed to; LM Studio, Jan.ai, and Ollama proved narrow scope plus a pull-based catalog is sustainable but never attempted the general-purpose "app store" framing at all. Genesis sits in unoccupied territory: a Tauri 2 ACL boundary that is structurally, not just conventionally, default-deny, combined with a transactional install ledger and a manifest schema that shows the user a Flatpak-style permissions diff before every mutation, is a genuinely differentiated product surface — user-visible checksums and freshness indicators at install time appear to be underbuilt across the entire category, per this research, which makes it a real opportunity rather than a solved problem to copy. The path to get there is disciplined sequencing: ship the Ollama-plus-terminals MVP, prove the approval-token-scoped-to-manifest-hash pipeline and the SQLite transaction log under real usage, wrap native package managers before ever writing a custom fetch-and-run engine, and only then widen the catalog axis by axis — IDEs via vendor hand-off, vision models with per-license tagging, and eventually community-submitted manifests gated by the same automated audit CI that Homebrew Cask and winget-pkgs already prove works at small-team scale.
